# Отчёт по индивидуальному заданию № 4
**Дисциплина:** Архитектура компьютера и операционные системы
**Тема:** Разработка имитационной программы с использованием протокола TCP для организации клиент-серверного взаимодействия

**Исполнитель:** Чернышов Роман Константинович, группа 252
**Вариант:** 6 — «Задача о каннибалах»

## 1. Условие задачи
Племя из нескольких дикарей питается из общего горшка ограниченной вместимости. Когда дикарь хочет есть, он забирает из горшка одну порцию. Если горшок пуст, первый обнаруживший это дикарь будит повара, после чего ожидает наполнения горшка. Остальные голодные дикари также ожидают, не создавая повторных запросов на одно и то же наполнение. Повар наполняет пустой горшок установленным количеством порций и снова засыпает. Наполнение не начинается, пока в горшке остаются порции. При необходимости источник порций можно дополнительно моделировать ограниченным запасом.

**Входные параметры:** количество дикарей; вместимость горшка; число приёмов пищи каждого участника; диапазоны времени между приёмами пищи; продолжительность приготовления; общий запас порций, если он ограничен.

**Отображаемые события:** попытка получить порцию, число оставшихся порций, обнаружение пустого горшка, пробуждение повара, начало и окончание приготовления, наполнение горшка, получение порции, завершение питания участника.

**Инварианты:** число порций в диапазоне от нуля до вместимости; одну порцию получает не более одного дикаря; одновременно горшок наполняет только повар; одно опустошение порождает не более одного актуального запроса повару; повар не перезаполняет непустой горшок.

**Завершение:** после выполнения заданного числа приёмов пищи; либо после исчерпания ограниченного запаса с корректным завершением ожидающих участников; либо по прерыванию пользователем, если задан режим неограниченного по времени выполнения. Повар и каждый дикарь являются самостоятельными участниками модели.

## 2. Анализ: разделение на программы
| Сущность | Есть собственное поведение? | Решение |
|---|---|---|
| Дикарь | да | отдельная клиентская программа `cannibals_savage`, по одному процессу на дикаря (семейство клиентов) |
| Повар | да | отдельная клиентская программа `cannibals_cook` |
| Горшок и запас порций | нет, но это общее состояние, которое должно быть согласовано | сервер `cannibals_server`: единственный владелец состояния, обрабатывает запросы последовательно |
| Наблюдатель | да: получает и показывает информацию | отдельная клиентская программа `cannibals_observer`, любое число экземпляров |

Решение о разделении принято исходя из целесообразности: у сети нет общей памяти и общих мьютексов, поэтому состояние горшка хранит один сервер, а повар и дикари превращаются в клиентов, которые общаются с ним сообщениями. Так сохраняются инварианты (все изменения горшка последовательны) и возможность подключать новых клиентов, в том числе наблюдателей.

## 3. Соответствие уровням требований
Реализована сразу программа наивысшего уровня, она включает все предыдущие.

| Уровень | Что реализовано |
|---|---|
| 4–5 баллов | сервер и клиенты (повар, дикари) независимо отображают то, что им пришло: сервер печатает события горшка, повар и дикарь только свои; IP-адреса и порты задаются в командной строке (`-a`, `-p`); работа на одном компьютере и по сети; завершение описано в разделе 6 |
| 6–7 баллов | отдельная клиентская программа-наблюдатель `cannibals_observer`, отображающая ход системы в целом |
| 8 баллов | множество наблюдателей, их можно подключать и отключать в любой момент без влияния на работу сервера |
| выше 8 | клиентов (повара, дикарей) можно отключать и подключать снова, сервер продолжает работать, а клиенты возобновляют работу; при завершении сервера все подключённые клиенты завершаются корректно |

## 4. Сценарий: сущности и взаимодействие
**Транспорт:** TCP, IPv4. Протокол текстовый, строки оканчиваются `\n`, поэтому его можно проверить обычным `nc`.

| Направление | Сообщения |
|---|---|
| клиент → сервер | `HELLO COOK`, `HELLO SAVAGE <id>`, `HELLO OBSERVER`; `TAKE` (дикарь хочет есть); `FILL <n>` (повар приготовил); `BYE` |
| сервер → клиент | `WELCOME` (параметры модели, число уже съеденных порций, время сервера); `REJECT <причина>` |
| сервер → дикарь | `GRANT <съедено>` (порция выдана), `STARVED` (запас исчерпан) |
| сервер → повар | `COOK` (проснись и готовь) |
| сервер → наблюдатель | `EV <мс> <текст>` (событие с временем), `TXT <текст>` (строка без времени) |
| сервер → все | `SHUTDOWN normal` или `SHUTDOWN stopped` |

**Сервер** работает в одном потоке на `poll()`, обслуживает слушающий сокет и все соединения (неблокирующие сокеты, у каждого своя очередь вывода). Состояние горшка меняется только при обработке одного сообщения, поэтому инварианты проверяются после каждого такта (`check`).

**Дикарь** подключается, получает параметры и число уже съеденных порций, ждёт случайную паузу, отправляет `TAKE` и ждёт ответ. Пока он ждёт, он слушает сокет, поэтому `SHUTDOWN` и обрыв соединения замечает сразу.

**Сервер на `TAKE`:** если порция есть, выдаёт её (`GRANT`); взявший последнюю порцию будит первого из очереди, тот обнаруживает пустой горшок. Если горшок пуст, фиксирует это, при отсутствии актуального запроса отправляет повару `COOK` (иначе дикарь встаёт в очередь без повторного запроса). Если запас исчерпан, дикарь получает `STARVED`, а следующий ожидающий разбирается по цепочке.

**Повар** ждёт `COOK`, «готовит» случайное время, слушая сервер, и отправляет `FILL <вместимость>`. Сервер сам проверяет, что запрос актуален и горшок пуст, ограничивает порции запасом, выдаёт порции ожидающим по очереди.

**Состояние клиентов на сервере.** Дикарь определяется номером: сервер помнит, сколько порций он съел, и статус (не подключался, активен, закончил, голодным ушёл). Повар один. Наблюдателей может быть сколько угодно.

## 5. Пользовательский интерфейс
Консольные программы, у каждой строки вида `[  1.234] Дикарь 3: получил порцию #1`. Время клиентов выравнивается по времени сервера при подключении (в `WELCOME` приходит время сервера). Параметры:
- **сервер:** `-a`, `-p`, `-n`, `-c`, `-m`, `-t MIN:MAX`, `-k MIN:MAX`, `-s`, `-r`, `-l`, `-i` (интерактивный ввод), `-h`;
- **клиенты:** `-a` (адрес сервера), `-p`, `-w` (сколько секунд пытаться подключиться), `-l`, у дикаря `-i ID`.

Параметры модели клиенты получают от сервера, поэтому их не нужно согласовывать вручную. Запуск на одной машине можно выполнить одной командой `scripts/run_local.sh`.

## 6. Варианты запуска и завершения
| Ситуация | Что происходит | Код |
|---|---|---|
| все дикари выполнили заданное число приёмов | сервер печатает итог, рассылает `SHUTDOWN normal`, все клиенты завершаются сами | 0 у всех |
| запас порций исчерпан | оставшиеся дикари получают `STARVED`, дальше так же | 0 |
| `Ctrl+C` / `SIGTERM` серверу (режим `-m 0`) | сервер печатает итог, рассылает `SHUTDOWN stopped`, клиенты завершаются | сервер 130, клиенты 0 |
| `Ctrl+C` клиенту | клиент закрывает соединение и завершается; сервер продолжает работу и ждёт его возвращения | 130 |
| сервер убит аварийно | клиенты видят обрыв соединения, сообщают об этом и завершаются | 1 |
| неверные параметры, порт занят, сервер не найден | сообщение об ошибке | 1 |
| `SIGUSR1` серверу | печатается состояние, работа продолжается | |

**Отключение и возврат клиентов (выше 8 баллов):**
- Дикарь отключился: его убирают из очереди ожидающих, его порции остаются учтёнными. При повторном подключении с тем же номером он продолжает с того места, где остановился. Дикарь, который уже наелся, получает отказ и сообщение, что он закончил.
- Повар отключился во время приготовления: запрос остаётся в силе. Когда повар подключается снова, сервер сразу посылает ему `COOK`.
- Нельзя подключить вторую копию той же роли: сервер отвечает `REJECT busy`.
- Медленный наблюдатель, чей буфер вывода превысил 64 КБ, отключается сервером, чтобы не задерживать остальных.

## 8. Тестирование
Скрипт `tests/run_tests.sh` запускает сервер и клиентов на одном компьютере, проверяет коды возврата всех программ, баланс порций, общее число съеденных порций и сообщения. Тесты:
- обычные запуски (5 дикарей, один дикарь, большой горшок, 40 клиентов-дикарей, нулевые паузы), ограниченный запас (исчерпание и достаточный запас);
- клиенты стартуют раньше сервера (порядок запуска не важен), 8 повторных запусков с разными seed;
- ошибки: неверные параметры, неверный адрес, занятый порт, сервер не найден, нет номера дикаря, неверный номер;
- адрес из командной строки: сервер на `127.0.0.2` недоступен по `127.0.0.1`;
- остановка сервера по `SIGINT` и по `SIGTERM`: все клиенты завершаются сами с кодом 0;
- `SIGUSR1`;
- подключение и отключение наблюдателей на ходу, снимок состояния для нового наблюдателя;
- отключение дикаря (`SIGKILL`) и повторный запуск с тем же номером;
- отключение повара (`SIGKILL`) во время приготовления и повторный запуск;
- отказ второй копии роли и неверного номера дикаря; закончивший дикарь не может вернуться;
- аварийная смерть сервера: клиенты завершаются с кодом 1 без зависаний;
- в конце: не осталось запущенных процессов.

Результат: 28 тестов из 28, два полных прогона подряд.

**Критическая оценка и правки, найденные при отладке:**
- Итоговая строка «===== Итог =====» содержала перевод строки внутри одного сообщения, и наблюдатель терял заголовок итога. Исправлено: заголовок передаётся отдельным сообщением.
- Если клиент подключался в момент завершения сервера, сервер закрывал соединение без объяснения, и наблюдатель завершался с ошибкой. Исправлено: `SHUTDOWN` отправляется всем открытым соединениям, а клиент при рукопожатии принимает его как штатное завершение.
- Сервер однопоточный (`poll`): это упрощает инварианты, но сервер не использует несколько ядер. Для такой нагрузки этого достаточно.
- Протокол без аутентификации и шифрования: любой, кто знает адрес, может занять роль дикаря с любым свободным номером или подключиться наблюдателем. Для учебной сети допустимо.
- Обрыв сети без закрытия соединения (например, отключили кабель) сервер заметит только по TCP keepalive, а с настройками по умолчанию это очень долго; процессы, завершившиеся штатно или аварийно, замечаются сразу.
- Только IPv4. Подключение к недоступному адресу ждёт стандартного таймаута `connect`.
- Если дикарь отключился и не вернулся, сервер ждёт его бесконечно (останавливается по `Ctrl+C`). Если не подключается повар, обед не продвигается.
- Максимум 100 дикарей и 256 одновременных соединений.

## 10. Выполнение дополнительных требований
Комментарии в коде; ввод-вывод через системные вызовы (`read`, `write`, `send`, `poll`, `socket`, `bind`, `listen`, `accept`, `connect`); тесты и скрипты запуска; журнал сервера (и опционально клиентов); воспроизводимый seed; интерактивный ввод параметров сервера; итоговая статистика; самопроверка инвариантов; работа с несколькими наблюдателями; переподключение клиентов с сохранением состояния; корректное завершение клиентов при остановке сервера.
