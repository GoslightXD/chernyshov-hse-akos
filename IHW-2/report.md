## 1. Условие задачи
Племя из нескольких дикарей питается из общего горшка ограниченной вместимости. Когда дикарь хочет есть, он забирает из горшка одну порцию. Если горшок пуст, первый обнаруживший это дикарь будит повара, после чего ожидает наполнения горшка. Остальные голодные дикари также ожидают, не создавая повторных запросов на одно и то же наполнение. Повар наполняет пустой горшок установленным количеством порций и снова засыпает. Наполнение не начинается, пока в горшке остаются порции. При необходимости источник порций можно дополнительно моделировать ограниченным запасом.

**Входные параметры:** количество дикарей; вместимость горшка; число приёмов пищи каждого участника; диапазоны времени между приёмами пищи; продолжительность приготовления; общий запас порций, если он ограничен.

**Отображаемые события:** попытка получить порцию, число оставшихся порций, обнаружение пустого горшка, пробуждение повара, начало и окончание приготовления, наполнение горшка, получение порции, завершение питания участника.

**Инварианты:** число порций в диапазоне от нуля до вместимости; одну порцию получает не более одного дикаря; одновременно горшок наполняет только повар; одно опустошение порождает не более одного актуального запроса повару; повар не перезаполняет непустой горшок.

**Завершение:** после выполнения заданного числа приёмов пищи; либо после исчерпания ограниченного запаса с корректным завершением ожидающих участников; либо по прерыванию пользователем, если задан режим неограниченного по времени выполнения. Повар и каждый дикарь являются самостоятельными участниками модели.

## 2. Анализ: какие сущности реализованы потоками
| Сущность | Есть собственное поведение? | Решение |
|---|---|---|
| Дикарь | да: периодически хочет есть, берёт порцию, ждёт повара | отдельный поток, N штук |
| Повар | да: спит, просыпается по запросу, готовит, наполняет горшок | отдельный поток |
| Горшок и запас порций | нет: пассивный разделяемый ресурс | структура данных под мьютексом |
| Очередь ожидающих повара | нет | часть разделяемого состояния |
| Обработка сигналов | служебная функция | отдельный поток с `sigwait` |
| Запуск, ожидание завершения, статистика | служебная функция | главный поток |

Итого N + 3 потока (N дикарей, повар, обработчик сигналов, главный поток). Все сущности с поведением представлены потоками, согласования числа потоков с преподавателем не требуется.

## 3. Как сущности отображаются в потоки и их взаимодействие
**Общее состояние** (структура `w` в `core.c`) защищено одним мьютексом `m`: число порций, остаток запаса, флаг «запрос повару уже сделан», очередь ожидающих, счётчики. Любое событие модели выполняется под этим мьютексом, поэтому события в журнале упорядочены, а инварианты проверяются в консистентном состоянии (функция `check()` после каждого значимого действия).

**Дикарь** (`savage_main`): цикл «поспать случайное время, затем под мьютексом попытаться взять порцию». Если порция есть, дикарь берёт её, а взявший последнюю будит первого в очереди ожидающих. Если горшок пуст, дикарь фиксирует это, и при отсутствии актуального запроса (`request_pending == 0`) будит повара, иначе просто встаёт в очередь. Затем дикарь блокируется до пробуждения и повторяет попытку. Если запас исчерпан, дикарь уходит голодным и будит следующего ожидающего (цепочка завершения).

**Повар** (`cook_main`): блокируется в ожидании запроса, проснувшись, готовит случайное время (мьютекс на это время отпущен), затем под мьютексом проверяет, что горшок пуст, кладёт `min(вместимость, остаток запаса)` порций, сбрасывает запрос и будит столько ожидающих, сколько положено порций.

**Как выполняются инварианты:**
- порции в диапазоне и «одну порцию получает один дикарь»: счётчик `pot` меняется только под мьютексом, баланс `положено - взято = в горшке` проверяется в `check()`;
- «наполняет только повар»: в программе единственный поток повара;
- «одно опустошение - один запрос»: запрос создаётся только при `pot == 0 && request_pending == 0`, флаг сбрасывается лишь при наполнении;
- «не перезаполнять непустой горшок»: проверка `pot == 0` перед наполнением, при нарушении аварийное завершение с кодом 2.

## 4. Синхропримитивы: две версии программы
Блокировка и пробуждение вынесены в интерфейс `sync.h`. Логика модели (`core.c`) общая, реализации разные:

| | `cannibals_sem` | `cannibals_cond` |
|---|---|---|
| Защита состояния | `pthread_mutex_t` | `pthread_mutex_t` |
| Ожидание повара | семафор `sem_t`, `sem_wait` / `sem_post` | `pthread_cond_t` + флаг запроса |
| Ожидание дикаря | свой семафор у каждого дикаря | своя `pthread_cond_t` + флаг пробуждения |
| Пробуждение при остановке | `sem_post` всем семафорам | флаги и `pthread_cond_signal` всем |

Ожидающие дикари стоят в FIFO-очереди и просыпаются по одному (столько, сколько положено порций). Это исключает «стадо» повторных попыток и не создаёт повторных запросов повару.

## 5. Пользовательский интерфейс
Консольное приложение для Linux. Каждая строка вывода имеет вид `[  1.234] Дикарь 3: получил порцию #1, в горшке осталось 1`, где в скобках реальное время от начала в секундах. Вывод идёт через `write(2)` в stdout и одновременно в журнал (открывается через `open(2)`), с буферизацией и общим мьютексом, чтобы строки потоков не перемешивались.

Параметры задаются аргументами командной строки (`-n`, `-c`, `-m`, `-t MIN:MAX`, `-k MIN:MAX`, `-s`, `-r`, `-l`, `-h`) или интерактивно (запуск без аргументов или с `-i`). Времена задаются в миллисекундах и выполняются как реальные паузы. Некорректные параметры отвергаются с сообщением и кодом 1.

## 6. Варианты запуска и завершения
| Запуск | Завершение | Код |
|---|---|---|
| `./cannibals_sem -n 5 -c 4 -m 3` | все дикари получили заданное число порций | 0 |
| `./cannibals_cond -n 4 -c 3 -m 5 -s 7` | запас исчерпан, ожидающие уходят голодными | 0 |
| `./cannibals_sem -m 0` | работает бесконечно до `SIGINT` / `SIGTERM` | 130 |
| неверные параметры | сообщение об ошибке | 1 |
| нарушение инварианта (не должно происходить) | аварийное завершение | 2 |

**Сигналы.** Во всех потоках сигналы заблокированы (`pthread_sigmask`), принимает их единственный поток через `sigwait`. Первый `SIGINT`/`SIGTERM` выставляет флаг остановки и будит все потоки, затем выводится статистика, журнал закрывается, код возврата 130. `SIGUSR1` выводит текущее состояние (порций в горшке, сколько ждут, чем занят повар) и работа продолжается. Повторный `SIGINT` при зависшей остановке завершает программу немедленно.

Примечание о воспроизводимости: seed определяет только случайные паузы. Порядок событий при одинаковых временах зависит от планировщика ОС, поэтому журналы разных запусков с одним seed могут немного различаться, а итоговые числа (сколько порций положено и взято) всегда согласованы.

Результат: 34 из 34 тестов пройдено.

**Критическая оценка:**
- Модель сделана так, что всё состояние защищено одним мьютексом, а потоки ждут вне его. Это просто и надёжно, но ограничивает параллелизм: реально параллельны только паузы дикарей и приготовление.
- Остановка по сигналу не мгновенная: спящие потоки проверяют флаг каждые 20 мс.
- Журнал сбрасывается блоками, поэтому при аварийном убийстве процесса (`SIGKILL`) последние строки могут быть потеряны.
- Версии на семафорах и условных переменных делят общую логику и отличаются только слоем блокировки, поэтому результаты у них должны совпадать; это подтверждено общим набором тестов.
